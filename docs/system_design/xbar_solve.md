# Crossbar DC solve

One array solve crosses the operation-level axis layout, the array holding geometry and physical state, the chunk loop bounding memory, the numerical solver leaf, the cell model, and the two boundary clamps evaluated during iteration. Each owner controls a disjoint part of the call, and the seams between them are where changing one end obliges the maintainer to read the other.

## Ownership across one solve

- **The macro** owns the semantic axes of an operation. It forms the complete leading shape, drives one value per word line as `[*leading_shape, row]`, samples BL/SL boundary conditions as `[*leading_shape, col]`, and identifies which leading axes jointly contain the WL phases sharing one boundary hold.
- **The array** owns geometry, the lattice constants, the cell sub-module, and the projection from a raw operating point to the state that survives. It reads the canonical leading shape from the line-level WL drive, distributes that drive across columns as `[*leading_shape, col, row]`, snapshots the cell once at the full call shape, packages the tensor-carrying inputs, and injects one function that calls its solver with explicit arguments and immediately projects the result. It uses the caller-named WL phase axes only to sum phase energy and charge one boundary establishment; it does not interpret the phases or own their layout. It holds no chunk loop and no numerical iteration state.
- **The chunk executor** owns memory tiling and nothing else. It slices every tensor field of one operand dataclass, calls the injected unary function, and folds every tensor field of its result dataclass. It knows no solver signature, module, constant, DCOP, or circuit meaning; those remain captured by the injected function rather than passing through the executor API.
- **The solver** owns the numerical method and no state. It is a function rather than a module or a preconfigured object; its immutable iteration config and every physical actor it needs arrive per call. The array selects it as an explicit code dependency — one array topology has one numerical implementation — so nothing on this path is registry dispatch; [construction](construction.md) covers what is.
- **The cell** owns the device stack. The array selects its concrete cell family, while the solver sees only the structural `ResistiveCell` role and repeatedly evaluates `solve_dc`; the common current and terminal derivatives are exposed through `ResistiveDcop`, while the concrete DCOP may carry additional state for the array. Construction, programming, and snapshotting are deliberately absent from that role. The cell condenses its own internal node, so the array system carries no per-cell unknown, the solver opens no device leaf, and no device current is stamped outside the cell. The sign contract on the two terminal conductances is consumed unchecked: a cell returning the wrong sign corrupts the solve silently rather than raising.
- **The boundaries** reach the solve as a structural role: the transfer law alone, evaluated at a port current against a snap the caller has already sampled. Sampling and delivery both stay outside the role, so a driver, a switched capacitor, or an amplifier held in clamp satisfies the same surface while each is constructed, snapshotted, and billed by the block that owns it.

Both rails' rest levels come off those same snaps. The nominal reference the role requires is the ideal level and carries no driver-owned offset or draw: the solve seeds its warm start from it, and the array measures capacitive displacement from it. That is why a concrete driver keeps its perturbations in fields of its own — billing against a perturbed reference would charge a driver's non-ideality to the array's capacitance.

## The array adds topology axes

Signals cross the macro–array boundary in the natural layout of the peripheral that produced them. The macro completes every workload and instance axis in `leading_shape`, but it does not expand a line-level signal over the array geometry. A word-line driver therefore supplies `[*leading_shape, row]`; the array distributes it over columns as a stride-0 `[*leading_shape, col, row]` view before snapshotting the cells. BL and SL clamps already have one port per physical column, so their snaps enter as `[*leading_shape, col]` and need no geometry expansion.

This is an ownership rule rather than a convenience for the current implementation. Column and row are topology axes, so only the array may decide how a peripheral-level signal reaches its cell sites. A later array that models word-line IR drop can replace uniform column distribution with its own network treatment without changing the macro or the driver interface. Conversely, the macro must not pass an incompletely broadcast semantic shape and expect the array to infer workload or instance axes; the array knows only that the complete leading shape precedes its terminal row or column axis.

## Why the solve is nested

The formulation — an outer clamp Newton around an inner coupled wire Newton, with every cell condensed at each step — and its well-posedness are the [solver spec](../reference/primitive/xbar/solver/col_bl_col_sl.md). What the decomposition buys the software is the ownership split above: each sub-problem is small enough for one component to own. The cell's condensation keeps every device unknown inside the cell; the clamp stays a transfer law evaluated per step rather than a solved mesh node, which is what lets a boundary be a role instead of a member of the array's module tree; and the wire system stays block-tridiagonal in the row index, which is what keeps the per-chunk working set a plain product of chunk, column, and row extent. A simultaneous Newton over every unknown would fuse the three into one system no single component could own.

## The chunk loop is a memory knob

`solve_chunk_size` bounds memory and moves no number: a call's results are bit-identical across chunk sizes, with noise on as well as off. Every per-call draw is taken before the loop, once, at the full call shape — [physical_state](physical_state.md) owns that rule — so a chunk is a re-view of positions that already exist rather than a sampling event of its own, and slicing acts on the finished snap object. Treat a numerical difference between two chunk sizes as a bug.

A value of zero bypasses coordinate construction, slicing, and folding and hands the canonical operand tree directly to the injected function. A positive value is an upper bound: the execution uses the smaller of that value and the call's complete leading extent, so a small call is never padded up to an oversized configured chunk. It creates one device-local offset vector at that effective size; each iteration translates the vector to the current contiguous interval and unravels only those coordinates. The fold writes the valid result prefix back through the same contiguous interval, so neither global write indices nor all-chunk coordinates remain resident.

What the knob bounds is the solver and projection working set, not every tensor allocated by the full call. A chunk's grid-shaped state — the node voltages and the wire Jacobian that dominates it — is projected and released before the next chunk, and the fold reassembles only the small result, so no raw DCOP grid survives the iteration. The full snap still exists for the whole call: broadcast fields can remain stride-0 views, but genuinely varying noise or state may occupy the full leading. Removing that storage would change snapshot and random-sampling semantics and is a separate design problem. During slicing, stride-0 axes are collapsed before indexing and re-expanded afterward, so each chunk materializes only what actually varies within that snap field.

Two things make a tuned value non-portable. The compiled per-chunk peak exceeds the eager one at the same size ([compile](compile.md)), and a caller that flattens a serialized axis into the column axis multiplies the columns of a single solve, so a size proven under one phase layout may be far too large under another.

## The projection belongs to the array

The solver returns a grid-shaped operating point, and what survives it is a modelling decision rather than a rank heuristic. The array therefore projects each DCOP immediately after its solver call, while the raw node grid is still available. The kernel array uses its compiled `_project_dcop` entry point for the standard projection; an extended concrete array overrides `_project_dcop_impl` to retain a topology-specific quantity such as a lookup current. Each projection returns one nested steady state plus any bookkeeping tensor. The standard bookkeeping tensor is the capacitive energy of each solved phase; after folding, the array sums the caller-named WL phase axes and adds one establishment of the shared BL/SL rest state. Reassembling the raw operating point instead would retain every node grid at the whole leading.

The executor remains unaware of this decision. Its operand dataclass carries every tensor that must be sliced together, including nested snaps, while the injected function captures modules and scalar constants and names every solver argument explicitly. This removes `**kwargs` without forcing different solver topologies into one interface: another array may inject a function with a completely different internal call.

The projected port state is folded back to the full leading before anything is delivered on it, because each boundary is billed on its own column instance axis, whereas a per-chunk delivery would expose the ravelled chunk axis. A projection keeps that axis intact and reduces only over axes behind it — tail padding puts duplicate positions on the chunk axis, which a reduction across it would count ([compile](compile.md)).

The solver entry point remains usable on its own — no array, no chunk loop, one fixed shape — for a caller that wants the raw operating point the array projection discards. Both paths settle the same system and must agree numerically.

## Probing a solve

A solve's iteration trajectory leaves through a co-located recorder, never through the return value. The emitter stays blind to who is listening: the eager wrapper reads the recorder's active slot once and hands the answer to the compiled leaf as a plain flag, the leaf emits the whole trajectory whenever that flag is set, and the recorder turns away on arrival what its own threshold does not want. Both placements are load-bearing — reading the slot inside the leaf would bake one answer into the graph, and gating at the emit site would specialize the graph on a recorder's policy — and [compile](compile.md) holds the gate mechanics.

Nothing on the emit path feeds back into the iteration, so a solve returns the same operating point bit-identically whether or not anything listens; what a probe changes is cost. A probed solve breaks the graph at every emission and retains one residual grid per rail per inner step for as long as the recorder is open, both scaling with the iteration counts, which is why production paths run unprobed. The stream carries the residuals rather than the iterates they were evaluated at — the residual is what a convergence or calibration consumer reads — so a probed solve retains a residual pair per step instead of the whole working state of every iterate.
