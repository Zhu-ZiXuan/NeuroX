# CimEngine base

The `CimEngine` registry root: the config root (macro + encoding + the two accumulator configs shared by every variant), the code-assembled `CimEnginePolicy`, and the machinery every variant shares — the `_init_engine_backend` construction helper, the sub-phase plane expansion `_unroll_sub_phase` with its static row mask, the hoisted value-range / ADC delegations, the shared `program` skeleton, the `_build_cim_macro` helper, and the `chunk_pad_along` primitive. `matmul` and the organize pair (`_organize_w` / `_organize_x`) stay abstract; each variant writes its accumulation pipeline end to end.

## Design decisions

- **Registry dispatch keyed on config type.** `from_config` looks up the impl registered for `type(config)` via `RegistryMixin`; adding a variant is one `@CimEngine.register_key(MyConfig)` line and never touches the base. The concrete config type is what the `_neurox_class` discriminator selects when the engine config nests inside a unit config.
- **A `ModuleBase` container, not a plain `nn.Module`.** The fabricate cascade recurses only into `FabricateMixin` children, so the engine must be one for `fabricate()` on the unit to reach the xbar. It is a container: `is_profile_target = False` (no own PPA — its children self-report), `_sample_fabricate_mismatch` is a pass, and `inst_shape = ()`.
- **Policy assembled in code, never deserialized.** `CimEnginePolicy` is a concrete dataclass the owning unit constructs from its own policy's `cim_macro` field; engine TOML sections carry config only.
- **The engine owns the sub-phase serialization.** The tile publishes one query — `max_active_rows` — and consumes pre-masked WL planes; the engine expands every WL drive over the hardware sub-phase axis (`P = ceil(row_num / max_active_rows)`) before calling `vec_mat_mul` and sums exactly that axis afterwards. The ceil covers every row when the tile geometry is non-divisible — the last sub-phase reads the short remainder block — and equals the exact quotient when `max_active_rows` divides `row_num` (so a uniform / linear geometry is unchanged). Centralizing the expansion in the engine base keeps the macro contract plane-in / code-out and makes the mask logic identical across variants.
- **Backend construction is one shared helper; the run path stays leaf-specific.** `_init_engine_backend(inst_shape, n_logical, w_parallel_size, row_tile_num)` builds the owned xbar, stores the tiling constants, derives `_sub_phase_num = ceil(row_num / max_active_rows)` and `_sub_phase_dim = -(len(inst_shape) + 2)`, and registers the static `[P, row_num]` row→sub-phase mask (`arange(row_num) // max_active_rows == arange(P).unsqueeze(-1)`, non-persistent; zero-fill = WL off — a non-divisible geometry's short final block owns only its own rows and every row is still covered). Each variant's organize and aggregate remain a matched pair whose reductions differ per variant (the organize/aggregate dual) — mixing one variant's organize with another's aggregate produces a wrong-but-plausible shape.
- **Value ranges are leaf-sourced, base-published.** The concrete `w_value_range` / `x_value_range` properties read the protected `_w_value_range` / `_x_value_range` attrs each leaf ctor sets once after building its transcoder/slicers (the sources differ per leaf); the ADC surface delegates to `self.xbar` directly.
- **`Sw` layout vs `Sa` schedule split.** `Sw` (per-weight slice count) is fixed at `program` time and held until the next `program`; `Sa` (per-activation slice count) is evaluated per `matmul` call and materialized by the simulator as a batched tensor axis. Fixed at different lifecycle points, the two cannot share a uniform slice-reduction helper, and the organize step lives on the W side only.
- **The base never reads variant config fields.** Before the xbar exists, a variant reads only `col_num` / `row_num` off the base `CimMacroConfig`; everything else (`w_digit_count`, `w_digit_radix`, `x_range`, `w_digit_range`) is read off the constructed `self.xbar` via its abstract properties.
- **`[Sa, Sw, Tc, Tr]` is the fixed leading-axis order.** Every variant's organized weight tensor places its present slice/tile axes in this canonical order ahead of the tile-owned `(data, D, row)` trailing block. A variant that does not use an axis omits it entirely rather than padding it size-1 (the `M=1` / `Sa=1` placeholders inserted for broadcast against the activation are a separate matter). Fixing the order across variants is what lets the aggregate reductions name their axes by a stable negative index.
- **No self-compiled forward.** Each variant's `matmul` is wrapped in `@torch.no_grad()` and runs eager — the library does not self-compile the forward ([compile contracts](../../../../compile/contracts.md)). The memory-sensitive cost is the tile read inside `self.xbar.vec_mat_mul`, whose heavy DC solve compiles as a separate regional leaf — see [array internals](../../../../primitive/xbar/array/_1t1r/array.md).

## Contracts & invariants

- **Uniform construction.** `from_config` builds every registered variant through one call shape (`config`, `policy`, `w_logical_shape`, `dtype`, `T__K`, `ideal_xbar`); narrowing or reordering the arguments breaks dispatch.
- **`_unroll_sub_phase` inserts P immediately left of the inst-aligned block.** It expands trailing `[row_num]` planes to `[..., P, *span, row_num]` via `torch.where` against the mask, where `*span` is the xbar's `inst_rank` axes and the insertion index is `max(-(inst_rank + 2), -(x.ndim + 1))` — right of all other batch axes, so right-aligned per-instance buffers can never collide with P. The axis is always present, size 1 when `active_row_num == row_num`; rows outside a plane's window are zeroed (WL off).
- **`matmul` owns the sub-phase expansion and the two-stage digital accumulation.** The engine expands WL planes over its sub-phase axis, the xbar returns per-plane codes with primitive trailing `[col_num]` and leading order preserved, and the engine sums exactly its own sub-phase axis at `dim = _sub_phase_dim` (`phase_accumulator`, a `SerialAccumulator` — the sub-phase axis is time-serial on one register per tile port, so it bills per arriving per-plane code) before the leaf-specific slice/tile reductions (`col_accumulator` on `Tc`, shift-adders on `Sa`/`Sw`). Different reduction axes are different circuit modules — separately fabricated, separately billed — never merged into one reduce.
- **The `program` skeleton is shared; `_organize_w` is the variant hook.** `program` shape-gates against the bound `w_logical_shape` and hands `_organize_w(weight)` to `xbar.program`; only the organize bodies are leaf-specific.
- **`_build_cim_macro` honours `ideal_xbar`.** When `ideal_xbar=True` the helper applies `.to_ideal()` and discards the passed `xbar_policy` in favour of an empty `IdealCimMacroPolicy`. The derived `inst_shape` is the per-instance multiplicity prefix; the xbar appends its own trailing `(col_num, w_digit_count, row_num)`.
- **`chunk_pad_along` is the one shared geometric primitive.** It right-pads an axis to a multiple of `chunk_size` then unflattens it into `(num_chunks, chunk_size)`, inserting the chunk axis immediately after. `pad_value` has no default. Every variant's tiling step funnels through it so the pad/unflatten convention is identical across variants.
- **The `[Sa, Sw, Tc, Tr]` order is load-bearing for the aggregate.** The aggregate reductions address their axes by negative index against the fixed leading-axis order; a variant that reorders or inserts an axis, or assumes an omitted axis is present, silently reduces the wrong dimension, so each variant's aggregate index set is variant-specific.
- **Fabrication cascades through children.** `FabricateMixin` auto-resamples the owned tile and reducers in registration order (xbar, then accumulators, then shift-adders); the engine registers no static state of its own.
