# Serialize

NeuroX's dataclass serialization machinery: the raw dict <-> file boundary for TOML / YAML; the recursive, type-checked dataclass <-> dict coercion; the `_neurox_class` polymorphic dispatch that instantiates a named subclass; and the `_neurox_use` / `_neurox_use_preset` directives and their preset composition that layer config fragments. Cross-cutting software utility, carrying no physics and owning no reference twin.

## Design decisions

- **A curated package boundary.** The package lives at `neurox/common/serialize/`, with four internal modules — `keys`, `file`, `build`, `compose` — that a caller never imports directly. `neurox/common/serialize/__init__.py` re-exports the public surface each internal module contributes; every consumer outside the package — `SerializeMixin`, tests — imports only from `neurox.common.serialize`, never from `neurox.common.serialize.build` or `.compose` or `.file` or `.keys` by path. Every name the boundary exports is itself bare — a plain function or `TypeVar`, with no leading underscore anywhere in the exported surface.
- **Four internal modules, one acyclic dependency chain.** `keys` (the three reserved `_neurox_*` string constants) and `file` (dict <-> file, TOML / YAML dispatch by suffix) sit at the bottom with no imports of each other or of the other two modules. `build` (dict <-> dataclass coercion, `_neurox_class` dispatch) imports only `keys`, for the class-discriminator constant — otherwise pure `stdlib` reflection. `compose` (directive-and-preset expansion, dict merging, file -> dict orchestration) imports `file` for raw reads and `keys` for all three directive/discriminator constants; it does not import `build`. The package `__init__` sits on top of all four, re-exporting the public names. No module imports downward from a higher layer, so the chain is acyclic.
- **Structure and directives layer on the file module, not on the parsers.** `compose` and `build` consume `file`'s raw `dict_from_file` / `dict_to_file` and add dataclass shape and NeuroX directive semantics above it; the TOML / YAML format boundary itself stays single-homed in `file`, so a config file remains loadable, diffable, and editable with off-the-shelf tooling.
- **The file root must be a table.** A loaded document whose top level is not a mapping is rejected at load time. A config is always a table of named sections, so a scalar or list root is a malformed file; catching it here keeps every downstream consumer free of the check.
- **`None` is stripped on TOML write.** TOML has no null literal, so a mapping value of `None` cannot be represented; `dict_to_toml` drops such keys recursively rather than emit an unwritable value. An unset field thus round-trips as an absent key, which a downstream loader restores from its default.
- **Receiver-bounded constructor.** `dataclass_from_dict` invoked for a `Root` resolves a `_neurox_class` name only within `Root`'s own subclass subtree: the returned instance is `Root` or one of its subclasses, never anything else. A discriminator that names a `ConcreteScheme` living outside `Root`'s subtree is an error, not a lookup that reaches across the class graph. A receiver therefore bounds what it can construct — a call on a narrow `Family` cannot be tricked by file data into building an unrelated type.
- **Abstract-base rule.** A config or policy class that has dataclass subclasses is a polymorphic base and cannot be constructed directly. Deserialization targeting such a base must resolve to a concrete leaf through a `_neurox_class` discriminator; a mapping that omits it — whether the base is the top-level target, a mid-tree name the discriminator itself supplies, or a base-typed nested field — raises rather than instantiating the base, and reports the concrete leaves it will accept. A `Family` that is only ever specialized thus cannot slip through as a half-formed instance: the file must name which `ConcreteScheme` it means.
- **The discriminator is emitted only where a family exists.** On dump, a class that participates in a polymorphic family — one with a dataclass ancestor or descendant — writes a `_neurox_class` tag so the round trip can re-select the leaf; a standalone dataclass with no relatives omits it and stays terse. The tag appears exactly when a sibling type could otherwise occupy the same field.
- **Directives live in ordinary string keys, not a custom file dialect.** A directive is an ordinary string-valued key (`_neurox_use = "<path>:<section>"`); a stock parser reads it as plain data. All include semantics live in `compose`'s resolution pass, so the mechanism adds no grammar to the file format.
- **Two directives, split by which base directory resolves the path.** `_neurox_use` resolves its path relative to the file that carries the directive; `_neurox_use_preset` resolves relative to the bundled presets root (`neurox/presets/`). The split tracks ownership: a user-authored fragment travels and versions with the referencing project and must be found beside it, whereas a bundled preset travels and versions with the package and must be found in the package no matter where the referencing file lives. A single shared base cannot honour both — resolving a preset against the referencing file would let a config that is moved or copied silently re-bind the preset to whatever happens to sit in the new directory.
- **Inline table and dotted key are the same directive.** `field = { _neurox_use_preset = "family/file:section" }` and `field._neurox_use_preset = "family/file:section"` parse to the identical `{"field": {"_neurox_use_preset": "family/file:section"}}` mapping — TOML's inline-table and dotted-key forms are interchangeable syntax for one nested table, and `compose` sees no difference between them. The dotted-key form reads tersest for a single-directive field with no other inline overrides.
- **A preset reference opens a closed, forward-only dependency graph.** Once resolution enters a fragment through `_neurox_use_preset` it stays in preset mode, where a nested `_neurox_use` is rejected, and a preset path may not be absolute, start with `./`, or contain a `..` segment. Together these confine every transitive reference of a preset to a forward path inside the presets root: a preset can depend only on other presets, never on a user file, and no reference can climb out of the package tree. A bundled preset's full dependency closure is therefore reproducible from the package alone.
- **Preset authority: the referenced fragment or preset is the sole `_neurox_class` owner.** A table carrying `_neurox_use` or `_neurox_use_preset` must not also declare `_neurox_class`, and this holds uniformly for both directives — the discriminator, if one is needed, belongs to the fragment being pulled in, not to the referencing site. A bundled preset itself carries no directive, so it is free to (and does) declare its own `_neurox_class` directly: a preset self-describes its concrete type. Inline keys beside a directive may still override ordinary field values; only `_neurox_class` is off-limits, since letting the referencing site override the type would let one reference silently retarget the fragment to an unrelated subclass.
- **Inline keys override the fragment, never the reverse.** A directive contributes a base table; the keys written inline beside it are layered on top and win every collision. A reference reads as "start from this fragment, then patch these fields", so one shared fragment can back many call sites that each adjust a few values without editing the fragment.
- **An unknown key fails loud instead of silently defaulting.** A key that matches no field of the target dataclass raises rather than being dropped. Silently ignoring it would let a misspelled parameter fall back to its default and ship a wrong number behind a config that looks correct. The same stance rules out a silent schema-migration layer — there is no version tag or field-rename map, so adapting a file written against an old field name is a deliberate manual edit.
- **Coercion is strict about primitives.** A `bool` is not accepted for an `int` field and a string is not accepted for a numeric field, even though Python's own `isinstance` would allow the first; only the widening a config round trip genuinely needs — an integer for a `float` field — is permitted. A type confusion in a file surfaces as a load error at the offending key, not as a silently mis-typed value.
