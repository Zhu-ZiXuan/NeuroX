# Xbar cell base

The pluggable-cell family: the solver-facing `XbarCell` contract plus its `XbarCellConfig` / `XbarCellPolicy` / `XbarCellSnap` / `XbarCellDcop` container bases. The base self-accounts no static PPA — its silicon is budgeted by its owner — and holds no cell-level mismatch, which its device children carry, so wiring and energy accounting sit above it.

## Design decisions

- **The cell is in the module tree, and self-accounts no static PPA.** A cell owns its device children, so it must be a module: buffers move with `.to` / `.eval`, and the fabricate cascade reaches the devices. The cell's silicon, and its devices', is budgeted by the owning circuit rather than self-accounted, so the cell sets `is_profile_target` false, which excludes it from the profiler's static walk and forbids it from emitting a dynamic event of its own. The cell only returns per-read node-capacitance switching energy via `dynamic_energy`, which its owner emits. That is why `XbarCellConfig` is a no-PPA base.
- **Pure contract on the base, config-keyed registry on the family root.** `XbarCell` is a solver-facing contract only — it carries no registry and no factory. The config-keyed registry plus a `from_config(*, config, policy, inst_shape, dtype, T__K)` classmethod live on each family root (`XbarCell1t1r`), mirroring the `CimMacro` precedent: a concrete cell registers itself with `@XbarCell1t1r.register_key(<ConcreteConfig>)`, and the owning array builds its cell via `XbarCell1t1r.from_config(...)`, so the cell model is selected purely by the concrete `cell_config` type the deserializer resolves from `_neurox_class`. The registry's key domain is that family's own config subtree, so dispatch is family-bounded by type — the resolved impl is always a member of the family and the array needs no post-build `isinstance` narrowing. Switching cell models is a config choice, not a code change.
- **Empty container bases, not shared fields.** `XbarCellConfig` / `XbarCellPolicy` / `XbarCellSnap` are markers: the family has no field every topology shares, so each cell topology carries its own subclass (its device or table configs, its per-device or empty policy, its snap fields plus control state). Only `XbarCellDcop` is a real base — its condensed branch triple (`i__uA`, `di_dvbl__uS`, `di_dvsl__uS`) is the surface every cell returns identically, so it is concrete and shared, and concrete cells subclass it to add their internal-node voltages. A cell's own residual, if it has one, is a separate payload submitted to its own co-located `Prober` subclass — never a `XbarCellDcop` field.
- **Type-parameterised so the typed surface survives subclassing.** `XbarCell` is `Generic[SnapT, DCOPT]` (bound to `XbarCellSnap` / `XbarCellDcop`). A concrete cell binds both vars to its own subclasses, so `snapshot` / `solve_branch` / `solve_dc` / `dynamic_energy` carry the concrete types with no LSP-narrowing override — these typed surfaces stay type-checked across topologies.
- **Internal nodes condensed in the cell, not the array solve.** `solve_branch` eliminates every internal node inside the cell and exposes only the condensed two-terminal branch through the typed `XbarCell[SnapT, DCOPT]` surface. The cell therefore binds to no particular solver and carries no solver state — it is a stateless per-call actor.
- **A cell's residual, if any, is submitted to its own co-located `Prober` subclass, not returned.** A topology whose condensation has an internal-KCL residual (e.g. the Detail 1T1R cell) declares its own `Prober` subclass beside its payload and, at the converged internal node inside `solve_dc`, computes that residual and submits it once per call — gated behind `if SomeLinkProber.active():` so an unsubscribed run never builds the diagnostic. A topology with no residual concept (e.g. the Linear 1T1R cell) declares no prober at all.

## Contracts & invariants

- **The abstract method set every cell implements.** `snapshot`, `program`, `solve_branch`, `solve_dc`, `dynamic_energy` are `@abstractmethod`; the owner builds the concrete cell through the family root's `XbarCell1t1r.from_config` registry dispatch. `solve_branch` is the lean hot path returning `(i__uA, di_dvbl__uS, di_dvsl__uS)`; `solve_dc` is its diagnostic / energy superset returning a concrete `XbarCellDcop` with internal-node state, and — for a cell that declares one — emitting its own internal-KCL residual on its probe channel. Both must condense identically. `dynamic_energy` consumes that converged `XbarCellDcop` from `solve_dc`, reading its internal-node voltages to charge the internal device caps — it needs those internal-node voltages, not the terminal voltages alone.
- **Signed-conductance contract.** Every implementation must return `di_dvbl__uS` non-negative and `di_dvsl__uS` non-positive; Reference fixes this sign convention as a family-wide branch invariant. The base validates neither sign — a violation raises no error and is caught nowhere — so the obligation rests entirely on each implementation.
- **Control and device samples travel in the snap.** `snapshot(control=..., shape=..., multi_coords=..., t_elapsed=...)` bundles the device snaps with the cell's exogenous control drive; `solve_branch` / `solve_dc` / `dynamic_energy` read the control only from the snap, never from `self`, so a single `snap` carries all per-call control and the cell holds no per-call control state. `shape` is the per-call broadcast shape `(*leading, col, row)` and `multi_coords` the advanced-index tuple selecting one chunk's positions (`None` for the full view); the cell forwards both to its device snaps so device samples stay aligned with the broadcast operating point.
- **`@torch.compile` constraints.** `solve_branch` executes inside a compiled region, so every concrete implementation obeys the same rules: no in-place tensor writes, no Python-side branches on tensor values.
