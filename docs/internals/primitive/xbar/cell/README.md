# Xbar cell base

The pluggable-cell family: the abstract `XbarCell` plus its `XbarCellConfig` / `XbarCellPolicy` / `XbarCellSnap` / `XbarCellDcop` / `XbarCellResiduals` container bases. The base self-accounts no static PPA — its silicon is budgeted by its owner — and holds no cell-level mismatch, which its device children carry, so wiring and energy accounting sit above it.

## Design decisions

- **The cell is in the module tree, and self-accounts no static PPA.** A cell owns its device children, so it must be a module: buffers move with `.to` / `.eval`, and the fabricate cascade reaches the devices. The cell's silicon, and its devices', is budgeted by the owning circuit rather than self-accounted, so the cell sets `is_profile_target` false, which excludes it from the profiler's static walk and forbids it from emitting a dynamic event of its own. The cell only returns per-read device-capacitor switching energy via `dynamic_energy`, which its owner emits. That is why `XbarCellConfig` is a no-PPA base.
- **The owner constructs the concrete cell directly.** A cell carries no registry and no `from_config`: the owning array builds its cell by concrete class name (`XbarCell1t1r(config=..., policy=..., inst_shape=..., dtype=..., T__K=...)`) from the `cell_config` sub-tree, the same owner-constructs-child discipline as the rest of NeuroX. A cell is a fixed structural member of its array, not a runtime-selected polymorphic family, so it needs no config-keyed dispatch.
- **Empty container bases, not shared fields.** `XbarCellConfig` / `XbarCellPolicy` / `XbarCellSnap` / `XbarCellResiduals` are markers: the family has no field every topology shares, so each concrete cell carries its own subclass (device configs, composite per-device policy, device snaps plus control state, internal residuals). Only `XbarCellDcop` is a real base — its condensed branch triple (`i__uA`, `di_dvbl__uS`, `di_dvsl__uS`) plus an optional `residuals` is the surface every cell returns identically, so it is concrete and shared, and concrete cells subclass it to add their internal-node voltages.
- **Type-parameterised so the typed surface survives subclassing.** `XbarCell` is `Generic[SnapT, DCOPT]` (bound to `XbarCellSnap` / `XbarCellDcop`), and `XbarCellDcop` is in turn `Generic[ResidualsT]` (bound to `XbarCellResiduals`). A concrete cell binds all three vars to its own subclasses, so `snapshot` / `solve_branch` / `solve_dc` / `dynamic_energy` and the DCOP `residuals` field carry the concrete types with no LSP-narrowing override — these typed surfaces stay type-checked across topologies.
- **Internal nodes condensed in the cell, not the array solve.** `solve_branch` eliminates every internal node inside the cell and exposes only the condensed two-terminal branch through the typed `XbarCell[SnapT, DCOPT]` surface. The cell therefore binds to no particular solver and carries no solver state — it is a stateless per-call actor.

## Contracts & invariants

- **The abstract method set every cell implements.** `snapshot`, `program`, `solve_branch`, `solve_dc`, `dynamic_energy` are `@abstractmethod`; the owner constructs the concrete cell directly (there is no `from_config` entry point). `solve_branch` is the lean hot path returning `(i__uA, di_dvbl__uS, di_dvsl__uS)`; `solve_dc` is its diagnostic / energy superset returning a concrete `XbarCellDcop` with internal-node state and, when `compute_residuals=True`, the internal-KCL residual. Both must condense identically. `dynamic_energy` consumes that converged `XbarCellDcop` from `solve_dc`, reading its internal-node voltages to charge the internal device caps — it needs those internal-node voltages, not the terminal voltages alone.
- **Signed-conductance contract.** Every implementation must return `di_dvbl__uS` non-negative and `di_dvsl__uS` non-positive; Reference fixes this sign convention as a family-wide branch invariant. The base validates neither sign — a violation raises no error and is caught nowhere — so the obligation rests entirely on each implementation.
- **Control and device samples travel in the snap.** `snapshot(control=..., shape=..., multi_coords=..., t_elapsed=...)` bundles the device snaps with the cell's exogenous control drive; `solve_branch` / `solve_dc` / `dynamic_energy` read the control only from the snap, never from `self`, so a single `snap` carries all per-call control and the cell holds no per-call control state. `shape` is the per-call broadcast shape `(*leading, col, row)` and `multi_coords` the advanced-index tuple selecting one chunk's positions (`None` for the full view); the cell forwards both to its device snaps so device samples stay aligned with the broadcast operating point.
- **`@torch.compile` constraints.** `solve_branch` executes inside a compiled region, so every concrete implementation obeys the same rules: no in-place tensor writes, no Python-side branches on tensor values.
