# Parallel BL/SL DC solver

The DC solve is one package of stateless, topology-specific software: the `Solver` interface and shared `SolverConfig` / `SolverDcop` containers, the concrete `NestedParallelRailSolver` (which also carries `SolverObservation` and its co-located `SolverProber`), the shared batched (block-)tridiagonal linear-algebra solves and wire-KCL builders, and the structural `ClampDriver` Protocol naming the boundary-clamp surface the solve consumes. The nested Newton formulation, its well-posedness, and the parallel-rail structural assumptions belong to the Reference spec; this document covers the software design and trade-offs.

## Design decisions

- **The solver is stateless and fixed to the parallel BL/SL topology, while remaining independent of concrete cell and driver implementations.** `Solver.__init__` takes only its numerical config and binds no boundary actors. `solve_dc` receives the cell, the BL driver, and the SL driver (plus their snaps) per call. The solver calls `cell.solve_branch(v_bl, v_sl, cell_snap)` at each wire-Newton step and assembles the block-$2\times2$ wire Jacobian from the returned single current and two signed conductances, and calls each driver's transfer law at each outer step; it stamps no device current, models no internal cell node, and hard-wires no concrete driver class.
- **The class is non-generic; `solve_dc` is method-generic.** The cell and driver types vary per call, not per construction, so the type parameters live on the method. `solve_dc` is generic over `(CellSnapT, CellDCOPT, BLSnapT, SLSnapT)`: the cell types retain their `XbarCellSnap` / `XbarCellDcop` bounds, and the driver snaps retain their `ClampSnap` bound. `SolverDcop` is `Generic[CellDCOPT]`, so the return type preserves the concrete cell DCOP instead of widening it to `Any`. Method-level parameters avoid a `**kwargs` boundary signature while keeping the complete surface type-checked.
- **Solvers are stateless tool classes, not `nn.Module`s.** They carry no buffers and no registered state, so they stay out of the core's module tree — otherwise the fabricate cascade and `state_dict` would wrongly sweep them in. The cell holds the device state; the solver holds the method (see [cell](cell/base.md)).
- **The owning array selects its solver explicitly.** A solver is a numerical implementation of one array topology, not a configurable physical module family. `XbarArray1t1r` therefore constructs `NestedParallelRailSolver` directly from `NestedParallelRailSolverConfig`; neither the solver nor its config participates in registry dispatch. The boundary actors remain per-call arguments of `solve_dc`, not construction-time fields.
- **The cell-grid layout is a fixed solver contract.** Cell-grid tensors use `[..., col, row]`, matching the array layout. The last axis follows the wire ladder through the rows, while the second-to-last axis indexes independent columns and their BL/SL driver pairs. The solver neither accepts an axis selector nor recursively rewrites cell snaps and DCOPs. A consuming array with another internal layout must organize its solver-boundary data into this contract because that array, not the numerical solver, owns the physical meaning of its dimensions.
- **Solvers have no Policy.** Every knob is either a workload-tuned numerical constant (`SolverConfig` subclass) or a method-intrinsic safety bound (`ClassVar` on the solver); none is a per-source non-ideality toggle.
- **Decompose the solve (nested) rather than one simultaneous Newton over all unknowns.** A simultaneous Newton over every wire / clamp unknown admits rail pseudo-equilibria and can leave a uA-scale BL wire residual; the nested block-Gauss-Seidel split into well-posed sub-problems eliminates both.
- **Iteration counts come from `calibrate_solver`, not hand-tuning** (chip-parameter-free step-ratio plateau; see [calibration guide](../../../guides/calibration/README.md)). The picker emits the raw plateau plus a fixed $+1$ outer margin; the resulting `n_outer` / `n_inner` are stored in the chip config and that is their only authoritative home. The per-cell condensation count `newton_iter_num` is calibrated separately and owned by the cell (see [cell](cell/base.md)).
- **Shared residual / driver-current builders for consistent diagnostics.** `col_wire_kcl_residual` and `col_driver_current` are the single source for per-column wire-ladder KCL and boundary current. Sharing them keeps residual diagnostics numerically identical across every solver that builds the same wire ladder, rather than each solver re-deriving the stamping.
- **Numerical solves accumulate into lists, never in-place.** Both Thomas sweeps (`solve_tridiagonal`) and the block-Thomas sweeps (`solve_block_tridiagonal`) accumulate intermediate results to stay compile-friendly. In-place tensor writes break `torch.compile` graph tracing; pure-functional accumulation lets inductor fuse the per-step elementwise ops across the unrolled loop.
- **Fixed shape convention for the block solver (no `dim` arg).** `solve_block_tridiagonal` fixes the $N$ axis as third-to-last for the block tensors (`[..., N, B, B]`) and second-to-last for the RHS (`[..., N, B]`); callers transpose at the call site if their layout differs. The scalar `solve_tridiagonal` instead takes an explicit `dim` because its slices are rank-uniform with the RHS and an axis argument costs nothing.
- **One block solve per step, not two.** The block forward sweep stacks the super-diagonal block and the RHS column into a single right-hand side and issues one block solve per row instead of two, then splits the result back into the coupling factor $C_k$ and the reduced RHS $d_k$.
- **Closed-form $2 \times 2$ block algebra.** Every block product and block solve in the Thomas and PCR paths routes through `block_matmul` / `block_solve`, which expand $B = 2$ into elementwise multiply-adds (adjugate/determinant form for the solve) and fall through to `@` / `torch.linalg.solve` for any other $B$. Batched GEMM / batched-LU kernels on tens of millions of $2 \times 2$ blocks cost orders of magnitude more per launch than the arithmetic they perform, and the elementwise form additionally fuses under `torch.compile`; the closed form matches LU to fp round-off in the diagonally-dominant wire-Jacobian regime.
- **Method-intrinsic damping caps are `ClassVar`s, not config.** They are per-iteration $|\Delta u|$ damping bounds (a Newton heuristic, not a chip parameter), so they never enter the calibrated config or any Policy. `NestedParallelRailSolver` carries an outer cap `MAX_OUTER_STEP__V` (applied to the coupled $2\times2$ clamp step) and an inner cap `MAX_INNER_STEP__V` (applied to the block-$2\times2$ wire step).

### Nested solver structure

The nested formulation is the Reference spec; the code realizes it in three phases. A **warm start** seeds the IR-drop wire voltages and the two boundary clamps. An **outer loop** of `n_outer` steps then runs clamp-first: each step takes one outer clamp-Newton step, then `n_inner` inner wire-Newton steps at the updated clamps, so the loop exits with the wire state already converged for the latest clamp and needs no post-loop consistency step. Every inner step calls `cell.solve_branch` for the branch current and signed conductances; the coupled block handles a variable-SL clamp through the same code path, with no special case. Both Newtons are damped by per-iteration $|\Delta u|$ caps. An **exit refresh** calls `cell.solve_dc` to re-align the returned cell DCOP and internal node with the final wire voltages, which the last inner step leaves stale.

The solve carries two kinds of scalar — calibrated iteration counts (`NestedParallelRailSolverConfig`, loaded from the chip config) and method-intrinsic damping caps (`ClassVar`s on the solver):

| Knob | Kind | Role |
|---|---|---|
| `n_outer` | config count | coupled outer Newton steps on $(V_{\mathrm{BL,CL}}, V_{\mathrm{SL,CL}})$ |
| `n_inner` | config count | inner block-Newton steps on the wire system per outer step |
| `MAX_OUTER_STEP__V` | ClassVar cap | outer-step $\lvert\Delta u\rvert$ damping cap |
| `MAX_INNER_STEP__V` | ClassVar cap | inner-step $\lvert\Delta u\rvert$ damping cap |

### The `ClampDriver` role

The solver's boundary-clamp dependency is the structural `ClampDriver` Protocol in `clamp.py`. It defines exactly two operations: `snapshot(*, v_ref__V, shape, multi_coords) -> SnapT`, which captures the per-call reference voltage in a `ClampSnap`, and `solve_clamp(i_port__uA, snap, *, v_clamp_init__V) -> (v_clamp__V, dVclamp_dI__MOhm)`. This is a capability role, not a registry base.

- **A role, not a base class.** A clamp driver is a horizontal capability the solve needs from a boundary, not a place in a class tree. A shared base would force a second inheritance axis and a least-common-denominator config. The Protocol captures only the thin surface the solver consumes, so conformance is structural rather than nominal.
- **Owned by the solver package.** Only the solve contract requires this surface, so the Protocol remains in `neurox/primitive/xbar/solver/` under the dependency-inversion rule that a role is defined with the operation that requires it.

## Contracts & invariants

- **The cell is the only device interface; the drivers are the only boundary interface.** The solver reads device behaviour exclusively through `cell.solve_branch` (hot path) and `cell.solve_dc` (final refresh), and boundary behaviour through each driver's clamp transfer, passing the snaps it received. It consumes the cell's condensed-branch and signed-conductance contract unchecked when assembling the wire Jacobian, so a cell that violates the signs silently corrupts the solve rather than raising.
- **`@torch.compile` constraints (compiled leaf).** `solve_dc` is a thin eager wrapper; the compiled unit is the inner `_solve_dc_compiled` leaf carrying the entire warm-start / outer / inner / exit-refresh solve. That leaf obeys: no in-place tensor writes; no Python-side branches on tensor values; no autograd reads of attributes that change across calls. Respecting them yields a single fused kernel over the solve, including the numerical solves it calls; the eager wrapper's probe guard sits outside the compiled graph entirely.
- **`SolverDcop` is the complete solve result.** It carries the wire and clamp state plus the condensed cell DCOP (`SolverDcop.cell`) behind one solver-independent data contract.
- **Residuals are demand-gated and submitted to a co-located `Prober`, not returned.** `solve_dc` is an eager wrapper around a `@torch.compile(dynamic=False)` leaf that returns only the converged `SolverDcop`; back in the eager wrapper, `if SolverProber.active():` gates the wire / clamp KCL residual computation, so the diagnostics are built and merged into a `SolverObservation` — and submitted exactly once via `SolverProber.submit(...)` — only when a `SolverProber` is active. The compiled leaf carries no probe logic, so the returned DCOP is bit-identical probed vs unprobed. Per-cell residuals remain inside the cell interface and are neither read nor forwarded.
- **Wire-ladder layout for the residual builders.** `col_wire_kcl_residual` and `col_driver_current` assume the wire runs along the row axis with the driver at the boundary. `segment_g` (shape `(row_num,)`) encodes the per-segment conductances along that wire; its ordering is boundary-dependent, with the driver segment at the boundary end and the cell-to-cell segments following toward the far end.
- **Sign / unit conventions.** The KCL residual is returned in uA with the convention $r = i_{\mathrm{inject}} + \Delta v_{\mathrm{left}} \cdot g_{\mathrm{left}} + \Delta v_{\mathrm{right}} \cdot g_{\mathrm{right}}$, where $\Delta v_{\mathrm{left}}[k] = v[k] - v[k-1]$ (and $v[0] - v_{\mathrm{drive}}$ at the driver end) and $\Delta v_{\mathrm{right}}[k] = v[k] - v[k+1]$ (zero at the far end, which has no right segment). Node voltages are V, segment conductances uS, currents uA.
- **Boundary slots are ignored, not validated.** In `solve_tridiagonal` the `sub` entry at index 0 and the `sup` entry at the last index are unused boundary slots; in `solve_block_tridiagonal` the `sub` block at $k=0$ and the `sup` block at $k=N-1$ are unused. The algorithms never read them — callers need not zero them.
- **Block-count semantics ($B$).** `solve_block_tridiagonal` works for any block size $B$ from the same code path: $B=1$ reduces to scalar Thomas and matches `solve_tridiagonal` numerically up to fp64 round-off, and $B=2$ is the coupled two-rail wire Newton the nested solver uses; larger $B$ runs through the identical sweep for any topology that couples more node classes per row. The single-block fast path ($N=1$) is one $B \times B$ `torch.linalg.solve`.
- **Elementwise derivative diagonal.** `elementwise_diff(fn, *, wrt, **kwargs)` returns the per-element derivative of an elementwise device function via one autograd backward pass. Because `fn` is elementwise, the derivative of the summed output with respect to each input element is that element's own derivative, so a single backward yields the full Jacobian diagonal without materialising off-diagonal terms.

## Performance & resources

- **Cell condensation sets the array memory.** Condensing the cell's internal node removes one unknown per cell from the array solve, so the wire Jacobian stays block-$2\times2$ (`[..., col, row, 2, 2]`) rather than carrying the internal node. The solver performs no leading-batch chunking.
- **Thomas vs block-Thomas cost.** Scalar Thomas is $O(N)$ elementwise work per system; block-Thomas is $O(N \cdot B^3)$ with one $B \times B$ solve per row, so memory stays $O(N \cdot B^2)$ per leading-batch instance. The block solver carries one extra trailing rank versus the scalar solver even at $B=1$.
- **Unrolled-loop fusion.** Because the sweeps build Python lists and `torch.stack` once, the per-step ops are pure-functional and inductor fuses the unrolled forward and back sweeps; there is no per-iteration kernel launch in the compiled graph.
- **No materialised dense matrix.** The Thomas path never assembles the full $N B \times N B$ system, so its per-instance memory does not scale with $N^2$.

## Gotchas

- **`B=1` block-Thomas is not bit-identical to scalar Thomas.** It agrees only up to fp64 round-off because the $1 \times 1$ `torch.linalg.solve` path differs arithmetically from the scalar division in `solve_tridiagonal`; the wire Newton uses $B=2$, but use the scalar helper when exact reproducibility against the scalar path matters.
- **`solve_block_tridiagonal` has no `dim` argument by design.** Passing data in a different axis order silently mis-indexes the block sweep rather than erroring; transpose to `[..., N, B, B]` / `[..., N, B]` before calling.
- **`segment_g` ordering is boundary-dependent — verify it matches the wire topology.** A mismatched ordering shifts every wire conductance and quietly corrupts the residual rather than erroring; `col_wire_kcl_residual` and `col_driver_current` share the same convention, so an inconsistency corrupts both.
- **Do not narrow `ClampDriver`'s `SnapT` bound below `ClampSnap`.** A concrete snap dataclass would turn structural conformance into an implementation dependency.
- **Do not re-bind the solver to a concrete clamp.** Replacing the per-call `ClampDriver[SnapT]` parameters with concrete stored fields would defeat the role boundary.

## Known limitations

- **No pivoting in the Thomas sweeps.** Both `solve_tridiagonal` and `solve_block_tridiagonal` assume the modified diagonal (block) stays non-singular through the forward sweep; they perform no row/block pivoting. Well-posedness is the responsibility of the Newton formulation, not these numerical solves.
- **Builders cover the column-oriented wire only.** `col_wire_kcl_residual` / `col_driver_current` are specialised to the `dim=-1` column wire; a row-oriented wire uses the sibling row-wire builders in the same module rather than a `dim` parameter on these.
- **Cell condensation is verified through residuals, not a global Jacobian.** Correctness rests on the solver's wire/clamp KCL residuals, the cell's own internal residual where applicable, and physical-vs-ideal agreement.
