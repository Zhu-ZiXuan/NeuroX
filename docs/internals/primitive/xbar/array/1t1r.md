# 1T1R array

`XbarArray1t1r` is the shape-independent pure array: it owns a pluggable [cell](../cell/1t1r.md) sub-module and the stateless solver, and holds its own lattice as config scalars rather than state. It owns no boundary driver, DAC, reference, or readout — those stay outside as peer blocks, injected into `solve_array` per call. It is the whole array family: one concrete class, extended by inheritance where a scheme's measurement carries more than the two boundaries.

## Design decisions

- **One concrete class, no abstract root.** A second array differs from this one by a measurement or a billing rule, not by a contract, and both are reachable by overriding a hook here. An abstract base would carry the entire body of this class and leave its subclass nothing to supply, so the family root and its only implementation are one class.
- **The config surface is the lattice and its two sub-trees.** `XbarArray1t1rConfig` states four per-node capacitances, two rail-link resistances, two cell pitches, and the cell and solver configs — nothing else. Every one of the eight scalars is a property of the uniform seat the tile repeats, so the tile is described once and the geometry (`row_num`, `col_num`) arrives at construction from the macro that places it.
- **The node-capacitance inventory belongs to the array, not the cell.** Each of `bl_node_c__fF`, `x_node_c__fF`, `sl_node_c__fF`, and `wl_node_c__fF` is one layout-extracted total: the cell's own junction at that node plus that node's share of the line hanging on it. The share is a grid quantity — it follows the pitch and the tile, so the same cell model dropped into another array carries another share — which is why the inventory sits on the holder's config while the cell states only its topology and its levels.
- **The array is where static PPA aggregates, and both numbers are derived.** A [cell](../cell/1t1r.md) and its devices self-account no static PPA, so the array — the first level that is a full electrical circuit — is the reporting node, and neither number is a config field. Area is the pitch lattice, the two cell pitches times the two counts. Leakage is structurally zero: both scan organizations rest at zero cell bias, so the tile holds no standing conduction path at all, and the conduction that flows under drive is the DC solve's, billed by the macro that owns the conduction window.
- **`_sample_fabricate_mismatch` is a documented no-op.** The array declares no per-instance state at all — cell mismatch is sampled through the `FabricateMixin` cascade into the cell children — so the override is an empty body, keeping `fabricate()` from re-raising the abstract hook while leaving the once-per-node resample untouched.
- **The array owns a pluggable `cell` sub-module, not the devices directly.** `XbarCell1t1r.from_config(...)` resolves the concrete cell model through the 1T1R family root's registry from the cell config sub-tree's `_neurox_class`. Dispatch is family-bounded by type, so the result is always a 1T1R-family cell with no post-build narrowing — which devices the cell owns, if any, is the cell's own business. The solver consumes the cell through its branch / snapshot contract and the energy path reads only family-base call outputs — the access-node voltage on the DCOP and the gate drive on the snap (see [cell](../cell/1t1r.md)) — so the array stamps no device current, opens no leaf, and reads no field back out of the cell config it handed over.
- **The array selects the numerical solver.** The parallel BL/SL topology fixes `NestedParallelRailSolver` as this array's implementation; `solver_config` supplies only its calibrated iteration counts. Solver selection is an explicit code dependency rather than registry dispatch driven by config data.
- **Two rails, taken as required init arguments.** `v_dd_wl__V` and `v_dd_bl__V` are constructor arguments, not config fields: they belong to the drivers a macro places around this array, so the macro defines them once at its own top level and cascades them down. They stay two variables even where a scheme sets them to the same number, because a term billed on the wrong rail is invisible while they agree. Which term rides which rail is fixed by [capacitive energy accounting](../../../../reference/primitive/physics.md).
- **`operation_mode` is an init argument and reaches the billing alone.** The scan organization is a property of the schedule the owning macro runs, so it is declared at construction. Nothing outside `_measure_chunk`'s energy branch reads it: `program` and `solve_array` are organization-blind, working on one node network and one physical state grid either way (see [scan organizations](../scan_organization.md)).
- **Drivers and their snaps are injected together, and the array normalizes neither.** `solve_array(v_wl, *, bl_driver, bl_driver_snap, sl_driver, sl_driver_snap)` takes each boundary as the structural `ClampDriver` role plus the snap already sampled from it. The caller owns the event structure — how many accesses one call covers, and which axes are correlated across them — so it is the caller that snapshots, and a snap that reached this array has already been shaped. The array widens nothing, checks no boundary rank, and constructs no driver, DAC, or reference of its own.
- **`v_wl` is a mandatory full cell grid.** A cell's control is the voltage at its own access-device gate, so `cell.snapshot(control=...)` takes `[..., col_num, row_num]` and the array passes the drive through unchanged. A caller that drives one line per row says so by expanding a row vector to the grid — a stride-0 view that costs nothing and states its correlation structure explicitly, which is what makes per-slot word-line noise expressible at all. Accepting a narrow vector and widening it here would silently assert the correlated case for every caller.
- **Both boundaries are returned; neither is delivered here.** The array calls no clamp forward: it hands each clamp to the solver and returns the reassembled port state of both rails at `[..., col_num]`, where the column axis is that clamp's own instance axis. Both are reported because both conduct — returning the bit-line pair alone would leave the source-line drive permanently unbillable — and the caller that injected the two clamps delivers each of them on that state, at the concrete type it holds. The full-leading state is what the caller needs, because a per-chunk delivery would bill a clamp bank against a ravelled chunk axis instead of its own column instance axis.
- **`program` is purely physical.** The state-index grid is `[*inst_shape, col_num, row_num]` and entry `(col, row)` is the state of the cell at that intersection. Digit placement, polarity pairing, and serial-slot layout are all the caller's; nothing about them is recoverable from, or asserted by, this method.
- **The measurement pair is the extension seam.** `_measure_chunk` folds one solved chunk into an `XbarArray1t1rChunkMeasure` and `_assemble_steady_state` turns the reassembled record into an `XbarArray1t1rSteadyState`. A scheme array whose measurement carries more than the two boundaries subclasses both records and overrides both methods, and its `solve_array` narrows the return type covariantly. Everything between — the snapshot, the chunk loop, the fold — is untouched by that extension, which is why the seam is two small methods rather than a re-implemented solve.
- **Each mode is one flat ledger, and the ledger is the whole account.** `_energy_wl_in_bl_scan__fJ` and `_energy_bl_in_wl_scan__fJ` each write out every bill of one solve in one place: the four node totals of every cell, each at the displacement its own node reaches. Nothing sits beside them, because every stretch of line is already inside the total of the node it hangs on. The first measures from ground; the second measures from the two boundaries' ideal levels and adds the rest state's own establishment divided by the row count. What separates them is precisely the rest state, which is what a scan organization *is*, so the two accounts are stated side by side rather than threaded through a shared body parameterized by the one thing that differs.
- **The rest state is declared, never solved.** The rest levels come off the snaps' nominal references, and the cells' internal access nodes rest at their own bit-line level — the storage element sits on the bit-line side of an access device orders of magnitude less conductive when off, so the off divider parks the node there. Resolving that divider would put a solved quantity inside a boundary the model otherwise declares, while the off-state wire IR drop next to it stays deliberately unsolved.
- **The lattice is uniform, boundary link included.** Ladder element zero is the link from the boundary to the first seat and spans one standard pitch like every other element, so one resistance per rail describes the whole ladder and no field describes a lead-in. Whatever extra reach a boundary driver needs to get from its own output to that first seat is a parasitic of the driver seat, stated and billed where that driver lives.
- **Chunking is delegated, not owned.** The array holds a `ChunkedSolver` wrapping `NestedParallelRailSolver` at `policy.solve_chunk_size` and makes exactly one `solve_dc` call at the original shapes; every slice, tail pad, and reassembly lives in that layer (see [chunked solver](../solver/chunked.md)). It passes down the broadcast leading it already computed — broadcast knowledge, not chunking knowledge — so nothing downstream has to recover which axes are leading. The broadcast leading reaches ~$10^5$ instances, and because the fold reassembles only the small per-instance measurement, `solve_chunk_size` bounds the whole call's peak — the wire Jacobian, $O(\mathrm{chunk}\times\mathrm{col}\times\mathrm{row})$ under block-Thomas, not merely the solver's own transient — and remains load-bearing; the array simply does not implement it.
- **Rail constants stay Python floats.** Each rail's link resistance goes from `self.config` into the `solve_dc` call as the scalar it is; the array registers no buffer for it and materializes no per-node profile, because a uniform ladder holds no information a repeated value would add. The capacitive account is scalar for the same reason: the four node totals are read straight off the config and broadcast against the node voltages.
- **The array owns no time axis, so it reports no duration.** The word-line grid and the conductance grid are both spatial — every row is driven and every cell conducts at once — so the array's own settling sits inside the window its owner already spans. Whatever a caller serializes on the array is that caller's schedule, and the caller times it.
- **Compile-path: the array is not the eager island.** `solve_array` traces; the eager island is `ChunkedSolver.solve_dc`, whose runtime trip count would otherwise unroll an enclosing compiled graph, and the compiled leaf is the per-chunk solver body at one fixed `(chunk_size, col, row)` cell-grid shape. See [compile/scheme_a_regional](../../../compile/scheme_a_regional.md).

## Contracts & invariants

- **`solve_array` returns an `XbarArray1t1rSteadyState`, not a DCOP.** The frozen struct carries the four port fields `i_bl_port__uA`, `v_bl_clamp__V`, `i_sl_port__uA`, and `v_sl_drive__V`, all `[..., col_num]`; dynamic energy is emitted internally through the `ProfileMixin` hook, not returned. The array builds no DCOP of its own.
- **The cap energy tensor is billed at the full leading, once.** The mode's energy function runs per chunk and the layer reassembles the result, so exactly one `[*leading]` tensor is emitted per call, its leading coming from broadcasting the WL drive against the weight grid: the caller's leading dims first, this array's own work axes next, its instance axes right-aligned last. The emission declares nothing about that layout — the collector keeps the caller's leading dims and sums the array's own work and instance axes past them. The cell's finer `(col, row)` axes are already folded inside the energy function, because the cell is not a profile target and this array logs on its behalf. The energy field is absent when no profiler asks for it, and the flag is constant across a call, so every chunk agrees on whether the field exists.
- **`weight_grid_shape` property.** The constructor takes the standard `inst_shape` replication prefix plus `row_num` and `col_num`; `weight_grid_shape` derives the full per-cell grid shape `(*inst_shape, col_num, row_num)`. The array owns this concatenation and passes the result to the cell as its `inst_shape`; it never derives geometry from lifecycle-produced cell state.
- **`program` validates the exact grid shape and nothing else.** A mismatch is a caller error that would otherwise corrupt every later solve silently, so it raises; row and column counts themselves are unguarded, a single row or a single column being a well-defined array.
- **One snap per call, at full shape.** The array builds `cell_snap` once at the full per-call shape and hands it, together with the two injected driver snaps, to the chunked solver as objects; the chunk slicing happens to the snaps, not to their construction. The array re-registers no child state.
- **Rest levels are the snaps' nominal references.** `bl_driver_snap.v_ref__V` and `sl_driver_snap.v_ref__V` are the ideal levels the boundaries declare, which is why a driver keeps its own offset and noise draws in separate snap fields; billing against a perturbed reference would charge a driver's non-ideality to the array's capacitance. Each cell's access node rests at its own bit-line reference, the same declaration read one node deeper.
- **Standalone solver access is a supported path.** Tests and solver-calibration tools that need the raw `SolverDcop` construct a solver and call `solver.solve_dc(...)` directly. The array path and the direct solver path must stay numerically consistent.

## Performance & resources

One term carries the call: the per-chunk working set, $O(\mathrm{chunk}\times\mathrm{col}\times\mathrm{row})$ under block-Thomas, which `solve_chunk_size` on `XbarArray1t1rPolicy` bounds, with `0` selecting the single-block path. What survives a chunk is per-column, $O(\mathrm{leading}\times\mathrm{col})$: the two port states and the scalar energy, kilobytes against the megabytes of node voltages the chunk itself held. At large-transformer-FFN scale an un-chunked leading batch reaches ~$10^5$ positions (~150 GB of node-voltage state), so chunking that working set is mandatory there. The snaps cost nothing to build at full shape: the branch-parameter fields and a row-uniform word-line grid are stride-0 views, materialized only where a chunk slice indexes them. Solver Jacobian storage dominates total memory — see [solver](../solver/nested.md).

## Gotchas

- **`solve_chunk_size` does not move the numbers.** Every per-call draw — driver offset and thermal noise, the cell's read noise — is taken once when the snaps are built at full shape, so the results are bit-identical across chunk sizes with noise on as well as off. Treat a numerical difference between two chunk sizes as a bug, not as RNG-stream drift.
- **A column-serialized caller flattens its own serial axis before it reaches here.** Column independence makes that flattening exact (see [scan organizations](../scan_organization.md)), but it multiplies the columns of a single solve, so a `solve_chunk_size` tuned against a per-group solve is far too large for the flattened one.
